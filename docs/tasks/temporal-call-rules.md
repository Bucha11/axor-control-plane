# Задача: правила по времени для вызовов инструментов («N за окно», «X только после Y»)

**Репозитории:** `axor-core` (ядро, обязательно первым) → `axor-wrap` (транспорт) → `axor-control-plane` (бэкенд, прокси, UI).
**Ветка во всех репо:** `claude/strands-box-axor-plain-9luyxz`.
**Источник идеи:** сравнение с Strands Box. Там политики Dogwood = Cedar плюс правила по истории событий (`formerly within 60s (...)`, `sum ... where`), состояние хранится в redb на каждый box. Копировать Dogwood **не нужно**: берём два самых полезных шаблона.

## Зачем

Сейчас у плейна одно правило со «состоянием» — общий лимит вызовов на сессию (`budget_cap_calls`). Им нельзя выразить:

- «`send_email` не больше 20 раз за 3600 с» (лимит за окно, на инструмент или группу инструментов);
- «`reset_password` только если в последние 3600 с был успешный `verify_identity` с тем же `user_name`» (последовательность с привязкой по аргументу).

Оба шаблона нужны оператору плейна, чтобы закрыть массовые действия и обход обязательного шага. Taint этого не покрывает.

## Решения, которые уже приняты (не пересматривай без причины)

1. **Два вида правил, без своего языка:**
   ```json
   {"id": "email-rate", "kind": "rate", "tools": ["send_email"], "max": 20, "window_s": 3600}
   {"id": "reset-after-verify", "kind": "after", "tool": "reset_password",
    "requires": "verify_identity", "within_s": 3600, "match_args": ["user_name"]}
   ```
   - `tools` в `rate` — список имён. Это может быть и роль из таксономии governor (`egress_sinks` и т. п.) под префиксом `role:`, например `role:egress`.
   - В `after` требуемый вызов должен **успешно выполниться** (через `register_output` / закрытие со статусом ok), а значения аргументов из `match_args` должны совпадать **точно** (сравнение через JCS-канонизацию, `axor_core.kernel.jcs.canonicalize`).
2. **Время детерминированное.** Решение принимается по временной метке вызова, а не по `time.time()` внутри гейта. Метка входит в событие трассы, и replay берёт её оттуда. Часы передаются в governor параметром (`clock: Callable[[], float]`), чтобы тесты и replay могли их подменить.
3. **Что считается.** `rate` считает **разрешённые** вызовы, то есть прошедшие `evaluate`. Отклонённые попытки в счётчик не входят: иначе агент, которому отказали, сам себе продлевает блокировку. Решение записать в docstring.
4. **Область действия:** сессия governor, как у taint-ленты. Счётчики на весь узел или на весь тенант в первой версии не делаются.
5. **Правила с плейна только ужесточают** (монотонность, как у `budget_cap_calls`). Правило с плейна можно добавить или сделать строже (меньше `max`, больше `window_s`/`within_s`), но нельзя ослабить или снять правило из манифеста узла. Слияние в `DesiredState.merge` должно сохранять это свойство. Снять правило с плейна — значит снять только то, что плейн сам добавил.
6. **`budget_cap_calls` остаётся как есть.** Обратная совместимость: старые узлы и старые трассы работают без изменений.
7. **Отказ.** Категория `budget` для `rate`, категория `sequence` для `after`. В причине — id правила и что именно не выполнено (например, «20 из 20 вызовов за 3600 с, следующий через 412 с», «нет успешного verify_identity с user_name=… за 3600 с»). В прокси `rate` отвечает 429 с `Retry-After`, `after` отвечает 403; для MCP `tools/call` — JSON-RPC ошибка, как сейчас.

## Шаги

### 1. axor-core
- Тип `TemporalRule` (две ветки: `rate`, `after`) с валидацией при загрузке. Неизвестный инструмент, `max < 1`, `window_s <= 0` и пустой `match_args` у `after` — ошибка, а не тихое игнорирование.
- История в `ToolCallGovernor`: метки разрешённых вызовов на каждое правило `rate` и успешные завершения для `after` с канонизированными значениями `match_args`. Память ограничена: хранить только записи внутри самого большого окна.
- Проверка в `evaluate` после существующих гейтов. Отказ идёт через `_denied()` с id правила в payload.
- В `DesiredState` новое поле `temporal_rules`, `merge` только ужесточает (п. 5). В `ControlDirectives` — метод получения.
- Replay: событие трассы несёт метку времени и id сработавшего правила. `kernel/replay.py` заново принимает решение по ним. Добавить правила в конфиг replay рядом с `budget_cap_calls`.
- Обновить `CHANGELOG.md`, поднять минорную версию.

### 2. axor-wrap
- `PlaneAdmission` / `PlaneLink` передают `temporal_rules` из желаемого состояния в governor, с той же проверкой подписи, что и остальные директивы.
- Чтение `temporal_rules` из манифестов (Config Builder / `axor-wrap manifest`).
- `bridge.py`: событие отказа по правилу попадает в схему событий плейна.

### 3. axor-control-plane
- **Бэкенд:**
  - `plane.py` принимает и валидирует `temporal_rules` в желаемом состоянии (только ужесточение — второй слой защиты рядом с ядром);
  - `audit.py` — новое действие `temporal_rules`;
  - `replay_api.py` — правила в конфиге replay.
  - Если правила хранятся отдельно от desired state — новая alembic-ревизия, `0001_baseline.py` не трогать.
- **Прокси** (`guard.py`): передать правила в governor сессии. Ответ 429 с `Retry-After` для `rate`, 403 для `after`, JSON-RPC ошибка для MCP. Трасса уходит на плейн, как остальные отказы.
- **UI:** на экране управления агентом — список правил: добавить, сделать строже, снять своё. Схему `DesiredState.schema.json` перегенерировать.
- В поиске шагов (`step_search`) отказы по этим правилам показываются как отказы правил, а не как «held»: это решение ядра, а не пауза оператора.

## Критерии готовности
- [ ] Тест в ядре: 21-й `send_email` за 3600 с отклонён, а после сдвига часов на `window_s` разрешён. Без изменения тест падает.
- [ ] Тест в ядре: `reset_password` отклонён без `verify_identity`; отклонён после `verify_identity` с другим `user_name`; отклонён после **неуспешного** `verify_identity`; разрешён после успешного с тем же `user_name` в пределах окна.
- [ ] Тест replay: трасса живого прогона с отказами по обоим правилам при повторном решении даёт те же вердикты, и время берётся из трассы, а не из часов.
- [ ] Тест монотонности: `merge` не даёт плейну ослабить правило из манифеста или увеличить `max`.
- [ ] E2E в плейне: правило, выставленное с плейна, через прокси в режиме `--guard` даёт 429 с `Retry-After`, отказ виден в трассе и в аудите.
- [ ] Старая трасса без `temporal_rules` проигрывается без изменений.
- [ ] `uv run pytest`, `uv run ruff check .`, `tsc` и `pnpm e2e` (там, где тронут фронт) зелёные во всех трёх репо.

## Чего не делать
- Свой язык политик, условия на тела и заголовки, суммы по байтам (как `sum` в Dogwood).
- Проверку значений **выхода** требуемого вызова (у Box есть `output.structured.verified: true`). Это можно добавить отдельной задачей, если понадобится.
- Счётчики на весь узел или тенант и хранение истории между перезапусками процесса.
- Подтверждение человеком.
